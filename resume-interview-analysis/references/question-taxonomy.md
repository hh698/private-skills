# 面试问题分类与追问覆盖矩阵

## 一、事实建模

先把简历内容放进三列：

| 类型 | 写法 | 面试使用规则 |
|---|---|---|
| 简历事实 | 原文能直接证明 | 可以用肯定句回答 |
| 合理推断 | 岗位常见关注点 | 只能写成准备题，不能冒充经历 |
| 待确认 | 缺数字、版本、个人占比或结果 | 给诚实回答，并标记按真实情况替换 |

## 二、板块与必问方向

### 个人与 HR

主问题：请做自我介绍、为什么换工作、为什么投这个岗位、期望薪资依据、职业规划、优缺点、能否接受加班/出差。

每个问题至少追问：具体例子、为什么这样判断、你本人做了什么、结果如何、如果重来会怎么做。薪资题要把岗位范围、经验、技能匹配和可协商空间说清楚，不能只说“市场就是这个价”。

### 时间线与经历

主问题：上一段工作做了什么、两段工作有什么变化、为什么从 GIS/项目测试转向自动化、工作空档如何安排。

追问顺序：当时的业务背景 -> 团队和本人职责 -> 日常产出 -> 一个难点 -> 结果证据 -> 离开的真实原因。时间、职位和项目周期与简历不一致时，优先提醒用户核对。

### 技能栈

按“会什么、用在哪里、怎么验证、遇到过什么坑、现在能否现场写”展开。技术分类包括：

- 测试流程、测试计划、风险、缺陷和上线判断；
- MySQL/Oracle/PostgreSQL/国产数据库、SQL 和数据校验；
- CentOS、国产操作系统、日志、进程、端口和权限；
- HTTP/TCP、Fiddler、浏览器开发者工具和接口排查；
- Postman、JMeter、Python、Pytest、Requests、Selenium、Playwright、Allure、Jenkins；
- K8S、微服务迁移、环境部署、回滚和稳定性；
- AI 工具：说明用于脚本初稿、测试数据、场景补全和日志整理，最终由本人核对和承担结果。

### 项目深挖

每个项目都使用以下链条：

`业务背景 -> 架构/模块 -> 你的角色 -> 测试范围 -> 环境与数据 -> 风险 -> 执行过程 -> 缺陷与协作 -> 结果 -> 复盘`

项目主问题之后，至少准备这些追问：

1. 为什么这个项目难？
2. 你具体负责哪一段，别人负责什么？
3. 你怎么设计测试策略和优先级？
4. 最严重的缺陷是什么，如何定位？
5. 测试数据和环境怎么准备？
6. 自动化为什么这样分层，维护成本如何？
7. 性能指标、基线、瓶颈和结论是什么？
8. 需求或开发延期时如何处理？
9. 如果没有你，项目会怎样？
10. 结果数字如何计算，个人贡献占多少？
11. 如果重来一次会改变什么？

第 9、10、11 类属于高风险主观/证据题，必须写得克制、具体、可核验，不能用“我很重要”“项目无法推进”这类夸大表述。

### 行为与冲突

用 STAR，但不要把 STAR 写成口号：背景一句、任务一句、行动写细、结果只写真实证据。必备场景：需求变更、开发不认缺陷、测试时间被压缩、线上故障、跨部门协作、重复性工作、失败复盘。

每题追问“你当时说了什么/做了什么”“对方为什么接受”“有没有副作用”“如何证明有效”。

### 现场实操

如果题目要求实际操作，答案必须包含最小可运行内容，而不是只描述流程。常见现场题清单见 `practical-questions.md`。

## 三、回答格式

每道题按以下格式输出：

```text
问题 N：……
面试官意图：……
推荐回答：……
追问 1：……
回答：……
追问 2：……
回答：……
可补充证据：……
边界提醒：……
```

追问不能只列标题；每一个追问都要有对应回答。若答案依赖用户确认，给出“目前能诚实说的是……”的版本，并明确替换点。

## 四、六项面试前必须准备的真实材料

根据简历和目标岗位，从以下六类中选出最适合的材料，每类都写“材料是什么、展示哪一部分、面试官可能问什么、候选人真实怎么答”：

1. 一页项目复盘：背景、本人职责、难点、证据和复盘。
2. 脱敏测试用例/缺陷样例：展示边界、优先级和缺陷闭环。
3. 自动化代码样例：目录、fixture、请求、断言、报告和维护方式。
4. 性能或稳定性分析：场景、参数、指标、瓶颈、结论和限制。
5. 环境/部署/排障记录：日志、命令、定位链路和回滚考虑。
6. 一份可现场演示的小题：接口、SQL、UI、Jenkins 或测试设计，确保能脱离公司环境复现。

不能把公司内部源码、客户数据或未获授权的截图带出；材料应使用自造数据或公开示例，并如实说明脱敏和限制。

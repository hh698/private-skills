# 简历面试问题与回答解析

## 目标

把一份真实简历转换成可直接复习、可现场表达、可继续追问的中文面试准备文档。输出要像候选人真正做过项目后的复盘：重点清楚、回答自然、有证据、有边界，不用模板化空话，也不凭空补造经历。

## 工作流程

### 1. 读取并建立事实底稿

先读取用户提供的简历。PDF 优先提取文本，同时检查页数、表格、图片和 OCR 风险；Word 读取段落、表格和标题。若内容来自截图或扫描件，标明需要人工复核的字段。

把内容分为三类：

- `简历事实`：姓名、岗位、时间、公司、项目、职责、工具、指标和学历等原文明确内容。
- `合理推断`：根据岗位和职责可以准备的问题，但不能写成已经发生过的事实。
- `待确认`：简历没有给出或无法核实的数字、版本、架构、个人占比和结果。

建立一张内部事实表：`板块 -> 原文事实 -> 面试官可能关注点 -> 可用证据 -> 风险/待确认项`。涉及业绩时严格区分公司/团队结果与个人贡献；涉及金额、比例、用户量、并发、缺陷数和性能数据时，不擅自改写。

### 2. 先做简历解构，再生成问题

按以下板块逐一生成问题，不要只挑所谓“重点题”：

1. 个人介绍、求职动机、岗位匹配、薪资和离职原因。
2. 教育背景、工作时间线、职业变化和空档期。
3. 技能栈：测试流程、数据库、Linux、网络、抓包、接口、UI、性能、持续集成、容器和 AI 工具。
4. 每段工作经历：工作内容、协作方式、质量责任、难点、成果、失败和复盘。
5. 每个项目：业务背景、架构、角色、测试范围、环境、数据、风险、缺陷、上线、指标和个人贡献。
6. 综合行为题：冲突、延期、需求变化、线上问题、优先级、压力、学习和自我评价。
7. 岗位实操题：现场写代码、SQL、接口断言、自动化框架、Jenkins、JMeter、Linux/K8S 命令和测试用例。
8. 面试前必须准备的真实材料：按当前简历调性给出六项可携带、可展示、可解释的材料及真实答案。

详细分类和覆盖矩阵见 [references/question-taxonomy.md](references/question-taxonomy.md)。

### 3. 每个主问题必须展开完整追问链

每个主问题至少包含：

- 面试官为什么问；
- 推荐回答；
- 追问 1、追问 2……（按自然面试顺序展开）；
- 每个追问的单独回答；
- 回答依据、可补充证据和不能越界的地方。

“可能追问”不是目录装饰，所有追问都必须写出答案。不能用“视情况而定”“可以结合项目回答”“同上”代替；如果真实信息缺失，应写成可诚实表达的版本，并标记`按真实情况替换`。

### 4. 主观题与客观题采用不同答法

主观题使用自然、克制、带具体经历的口吻。例如“如果没有你，项目会怎样？”不要夸大成“项目一定无法上线”，应说明自己承担的环节、风险、交接影响和团队仍可替代的部分。

客观题直接回答原理、步骤、判断标准和常见坑。技术题优先给出可执行内容：代码、SQL、请求示例、断言、目录结构、配置、命令或排查顺序。回答必须与简历中的工具和经历一致；没有用过的技术要明确“了解/练习过/未在生产使用”。

### 5. 识别并补强现场实操题

看到以下措辞时，必须给出真正能写出来或执行的答案，而不是只给思路：`现场写`、`手写`、`代码`、`SQL`、`怎么实现`、`怎么配置`、`给出命令`、`如何断言`、`如何排查`、`设计用例`。

至少覆盖与简历匹配的题型：

- Python + Pytest + Requests 接口自动化：请求、鉴权、参数、断言、异常和可运行结构。
- Postman：Tests 脚本、状态码、JSON 字段、业务码和环境变量。
- SQL：查询、分组、重复数据、关联、分页、数据一致性和参数化。
- Selenium/Playwright：定位、等待、Page Object、失败截图或日志。
- JMeter：线程组、参数化、关联、断言、监听器取舍和结果分析。
- Jenkins：流水线、依赖安装、测试执行、Allure 报告和失败退出码。
- Linux/K8S：日志、进程、端口、Pod、Service、部署和回滚的常用命令。
- 测试设计：登录、上传、权限、分页、导入导出、接口幂等和异常场景。

模板与示例见 [references/practical-questions.md](references/practical-questions.md)。代码应短而完整，优先能在面试白板或编辑器中解释；敏感地址、账号和真实数据使用占位符。

### 6. 生成文档

默认生成 `.docx`；如果用户只要求文字，也可先输出 Markdown。DOCX 结构建议为：

1. 标题、适用岗位、简历事实边界和使用说明。
2. 简历画像与面试官关注点。
3. 按板块排列的主问题与全量追问详答。
4. 现场实操题与可直接书写的代码/SQL/命令。
5. 六项面试前真实材料及对应答案。
6. 诚实边界、易被追问的风险点和面试前复习顺序。

问题编号稳定、层级清晰；代码使用等宽字体或代码段；每道题的追问都放在主问题下方，不能拆散到文末。生成 DOCX 后按文档工具的规范渲染为图片检查分页、代码换行、表格溢出、标题层级和中文字体，再交付最终文件。若用户指定目录，先检查目录和同名文件，默认使用带版本/日期的新文件名，除非用户明确允许覆盖。

## 事实与安全边界

- 不编造公司、项目、客户、金额、并发、缺陷率、职责占比、技术版本或上线结果。
- 不把团队成果写成个人独立成果；用“我负责……，团队完成……”拆分表达。
- 不把“接触过”升级为“熟练掌握”，不把练习代码包装成生产代码。
- 用户未提供的答案用“建议回答框架 + 按真实情况替换”处理，并列出面试前必须核实的事实。
- 不把原始简历、身份证、电话、邮箱、公司内部截图、真实接口、Cookie、账号、生成的个人面试文档放进公共仓库或 Skill 目录。
- Skill 本身只保存通用规则、脱敏示例和模板，不保存某个候选人的隐私信息。

## 交付前自检

- 是否覆盖简历的每个主要板块和每个项目？
- 每个主问题下的每个追问是否都有单独回答？
- 主观题是否像真实候选人的口吻，且没有夸大？
- 客观题是否给出准确、可执行、与简历匹配的答案？
- 所有现场实操题是否有可写出的代码、SQL、配置、命令或用例？
- 六项真实材料是否给出具体材料、用途、展示方式和真实答案？
- 所有数字是否有出处，未知项是否显式标记？
- DOCX 是否经过渲染检查，输出是否未覆盖既有文件？
